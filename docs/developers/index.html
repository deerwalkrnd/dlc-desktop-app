Developer guide

Architecture​

The app is a single Go binary with the SvelteKit web app embedded in it.

DLC/ folder ──scan──▶ in-memory catalogue ──JSON API──▶ SvelteKit SPA (in the browser)
                                         └─/media/{id}─▶ <video> (HTTP range requests)
  • No database. Every piece of information comes from file names, so the catalogue is rebuilt from the folder at startup (milliseconds for thousands of files) and on Rescan. Rescans build a new immutable index and swap it in atomically.
  • Stable IDs. Lesson IDs are a hash of the file path, and subject slugs come from the name and syllabus, so URLs survive rescans and restarts.
  • No third-party Go dependencies. Only the standard library is used.
PathPurpose
cmd/dlc-desktop-appEntry point: flags, library path, browser launch, shutdown
cmd/dlc-checkCLI that validates a video folder
internal/catalogPure filename parser (with the legacy-compatibility guarantee)
internal/libraryFolder scan → immutable index; safe file opening (os.Root)
internal/serverHTTP API, media streaming, SPA serving, security middleware
web/SvelteKit app; web/embed.go embeds web/build
internal/winresWrites the Windows icon, version info and manifest (.syso)
tools/winresCommand that make release runs to generate those resources
assets/windows/App icon sizes (from the Deerwalk logo)
scripts/Demo-library generator, release README, Windows signing script

Building​

Requirements: Go 1.27+ (the toolchain is pinned in go.mod and downloaded automatically), Node.js 22.18+, make, and optionally ffmpeg for the demo library.

The frontend uses SvelteKit 3 with Svelte 5. There is no svelte.config.js: SvelteKit is configured in web/vite.config.ts, and shared code is imported through the #lib/… alias declared in web/package.json "imports", with file extensions (#lib/api.ts).

make            # web app + bin/dlc-desktop-app + bin/dlc-check
make test       # Go tests (race detector) + frontend unit tests
make lint       # go vet, gofmt, svelte-check, eslint, prettier
make demo       # creates ./DLC with playable sample lessons (needs ffmpeg)
make run        # build and start against ./DLC
make release    # dist/*.zip for Windows and Linux

Without the frontend build, the Go binary still compiles and serves the API. The browser then shows a page explaining how to build the web app.

Development workflow​

Run the API server and the Vite dev server side by side:

make demo                                     # once
go run ./cmd/dlc-desktop-app -open=false      # API on :3000
cd web && npm run dev                         # UI with hot reload on :5173

Vite proxies /api and /media to the Go server (see web/vite.config.ts).

The filename parser and compatibility​

internal/catalog first splits names on every -, exactly like version 1.x. Only if that fails does it split on -. As a result, every name that parsed in 1.x parses to the same result. legacy_test.go keeps a verbatim copy of the old parser, and FuzzLegacyCompatibility checks this property on arbitrary input:

go test ./internal/catalog -run '^$' -fuzz FuzzLegacyCompatibility -fuzztime 60s

There are two intentional differences, both modelled explicitly in the test oracle:

  • the syllabus is case-insensitive, so old means the old syllabus (1.x treated anything but exactly OLD as new);
  • lesson numbers such as NaN, Inf and negative numbers are rejected. 1.x turned them into nonsense chapter numbers.

Video player​

web/src/lib/player.ts is an explicit state machine (idle → loading → paused ⇄ playing ⇄ buffering → ended, plus error). VideoPlayer.svelte translates <video> events into machine events and renders from the state.

Watch progress is frontend-only. web/src/lib/progress.ts holds the pure rules (when to resume, when a lesson counts as watched, storage validation), and progress.svelte.ts is a reactive store saved in localStorage under dlc.progress.v1 and kept in sync across tabs. The open lesson lives in the URL (?lesson=<id>), so search results and Continue watching link straight to a playing lesson.

Run the frontend unit tests (player, progress, highlighting) with npm test in web/.

HTTP API​

All responses are JSON. Errors look like {"error": "message"}.

Method & pathReturns
GET /api/classes{classes: [{number, subjectCount, lessonCount, syllabi}]}
GET /api/classes/{n}[?syllabus=old|new]{number, syllabi, subjects: [{slug, name, syllabus, chapterCount, lessonCount}]}
GET /api/classes/{n}/subjects/{slug}{class, slug, name, syllabus, chapters: [{number, title, lessons: [{id, number, title, teacher, mediaUrl}]}]}
GET /api/teachers{teachers: [{name, lessonCount, subjects}]}
GET /api/search?q=…[&limit=50]{query, total, results: [{class, subjectSlug, subjectName, syllabus, chapterNumber, chapterTitle, lesson}]}. Every word must match; title matches rank first; limit is at most 200
GET /api/libraryFolder, counts, scan time, skipped and warnings lists, version
POST /api/library/rescanRescans, then returns the same as GET /api/library
GET /media/{id}The video file, with range-request support
GET /healthz{ok, app, version}

Security model​

The server binds to 127.0.0.1 by default and:

  • rejects requests whose Host header isn't a loopback name, which blocks DNS-rebinding attacks from websites,
  • sends no CORS headers, so other websites can't read the API,
  • rejects cross-site POST requests (Origin / Sec-Fetch-Site checks),
  • serves videos only by ID, opening files through os.Root so that paths, .. and symlinks can't escape the library folder, and never lists directories,
  • sends nosniff, X-Frame-Options: DENY and Referrer-Policy headers.

With -addr 0.0.0.0:… (LAN mode) the Host check is turned off, since clients connect by IP address.

Releasing​

  1. Move the Unreleased entries in CHANGELOG.md under the new version.
  2. Push a tag such as v2.0.1 from main. The Release workflow runs the tests, builds the Windows and Linux archives and publishes a GitHub release.

make release first runs make winres, which writes cmd/*/rsrc_windows_amd64.syso (ignored by git). The Go linker embeds these in Windows builds, giving the executables their icon, version details and a manifest (Windows 10/11, no elevation, long paths). It uses a small standard-library generator in internal/winres, so no extra tools are needed.

Code signing (optional)​

Unsigned executables make Windows SmartScreen warn about an "unknown publisher" the first time they run. To sign releases, buy a code-signing certificate and add two repository secrets: WINDOWS_CERT_PFX (the .pfx file, base64-encoded) and WINDOWS_CERT_PASSWORD. The release workflow then signs both executables with scripts/sign-windows.sh (osslsigncode). Locally: make release SIGN=scripts/sign-windows.sh with the same two variables set, WINDOWS_CERT_PFX pointing at the file.
